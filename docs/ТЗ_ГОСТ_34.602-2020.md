## 2. Цели и назначение создания автоматизированной системы

### 2.1. Назначение системы

Система предназначена для:

1. регистрации приходных и расходных кассовых документов в кассах организации;
2. ведения кассовых смен, межкассовых перемещений наличных и инвентаризаций кассы;
3. учёта задолженностей контрагентов, денежных средств, собранных торговыми представителями, и сумм, выданных под отчёт сотрудникам;
4. контроля расходов через процедуру согласования руководителем;
5. формирования кассовой книги и аналитических отчётов;
6. обеспечения неизменяемости проведённых документов, журнала аудита и сохранности данных.

Система используется работниками бухгалтерии, кассирами, руководителями, аудиторами и администратором ООО «Фаиза» во всех филиалах организации.

### 2.2. Цели создания системы

| № | Цель | Критерий достижения |
|---|---|---|
| Ц-1 | Заменить ручное ведение кассовой книги электронным журналом | Все кассовые документы регистрируются в Системе; номер документа присваивается автоматически без пропусков и дублей в пределах кассы, вида документа и года |
| Ц-2 | Исключить кассовые ошибки, которые возникают из-за отрицательного остатка и превышения лимита кассы | Система отклоняет 100 % попыток провести документ, приводящий к отрицательному остатку на любую дату или к превышению лимита |
| Ц-3 | Обеспечить достоверность учётных данных | Проведённый документ и запись журнала аудита невозможно изменить или удалить ни через интерфейс, ни прямым запросом к базе данных |
| Ц-4 | Разделить обязанности | Администратор не может выполнять финансовые операции; автор расхода не может его согласовать |
| Ц-5 | Ускорить подготовку отчётности | Кассовая книга за период формируется в форматах экрана, CSV и PDF без ручного пересчёта |
| Ц-6 | Контролировать подотчётные суммы и расходы | Просроченные авансы и расходы, ожидающие согласования, видны на панели показателей |
| Ц-7 | Обеспечить сохранность данных при авариях | Резервная копия создаётся по расписанию, зашифрована и проходит автоматическую проверку восстановления |

Количественные цели (сокращение времени на операции, числа ошибок) задаются после обследования объекта: `[УТОЧНИТЬ У ЗАКАЗЧИКА: текущее время оформления одного документа, закрытия дня, подготовки кассовой книги за месяц; число выявленных ошибок/расхождений за период]`.

## 4. Требования к автоматизированной системе

### 4.1. Требования к системе в целом

#### 4.1.1. Требования к структуре и функционированию системы

1. Система должна быть построена по клиент-серверной архитектуре: веб-клиент (браузер), сервер приложений, сервер базы данных, обратный прокси-сервер с поддержкой TLS.
2. В составе Системы должны быть выделены подсистемы:

| Код | Подсистема | Назначение |
|---|---|---|
| ПС-1 | Безопасность и доступ | Аутентификация, сеансы, роли, доступ к кассам |
| ПС-2 | Нормативно-справочная информация | Организация, филиалы, кассы, валюты, курсы, номиналы, категории, контрагенты, типы документов |
| ПС-3 | Кассовые операции | Смены, документы, согласование, проведение, сторно, переводы, вложения |
| ПС-4 | Расчёты | Задолженности, платежи, квитанции представителей, авансы |
| ПС-5 | Контроль наличности | Пересчёт по купюрам, инвентаризация кассы |
| ПС-6 | Отчётность и аналитика | Кассовая книга, отчёты, панель показателей, уведомления |
| ПС-7 | Аудит и администрирование | Журнал аудита, резервное копирование, панель состояния системы |

3. Взаимодействие клиента с сервером должно выполняться по протоколу HTTPS в формате JSON; ошибки должны возвращаться в формате RFC 7807 (Problem Details) с текстом на русском языке.
4. Денежные суммы в обмене данными должны передаваться строкой с двумя знаками после запятой, без использования чисел с плавающей точкой.
5. Все даты «сегодня» и границы дня должны определяться в часовом поясе организации (Asia/Dushanbe).

#### 4.1.2. Режимы функционирования

| Режим | Описание |
|---|---|
| Штатный | Круглосуточная доступность для пользователей; плановое резервное копирование выполняется без остановки |
| Сервисный | Обновление версии и применение изменений схемы БД; сервер приложений не должен запускаться при неприменённых изменениях схемы |
| Аварийный | Восстановление из резервной копии по регламенту руководства администратора |

#### 4.1.3. Требования к численности и квалификации персонала

1. Для эксплуатации требуется один администратор Системы (может совмещать обязанности с другими ИТ-функциями, но не с финансовыми ролями).
2. Пользователи должны владеть навыками работы с веб-браузером; специальной подготовки, кроме ознакомления с руководством пользователя (1–2 часа), не требуется.
3. Администратор должен владеть основами администрирования Linux/Windows-сервера, контейнерной платформы и СУБД PostgreSQL.
4. Численность пользователей по ролям — `[УТОЧНИТЬ У ЗАКАЗЧИКА]`.

#### 4.1.4. Показатели назначения

| № | Показатель | Значение |
|---|---|---|
| ПН-1 | Число одновременно работающих пользователей | не менее 20 `[УТОЧНИТЬ У ЗАКАЗЧИКА: фактическая потребность]` |
| ПН-2 | Время ответа панели показателей при 20 одновременных читателях | 95-й перцентиль не более 500 мс |
| ПН-3 | Максимальная сумма документа | 9 999 999 999 999 999,99 |
| ПН-4 | Точность денежных сумм | 2 знака после запятой |
| ПН-5 | Размер страницы списка | не более 500 записей (журнал аудита — не более 100) |

Система должна допускать увеличение числа касс, филиалов и пользователей без изменения программного обеспечения.

#### 4.1.5. Требования к надёжности

1. Система должна сохранять согласованность данных при одновременной работе нескольких пользователей с одной кассой: одновременное проведение двух расходов, совокупно превышающих остаток, должно приводить к проведению не более одного из них.
2. Повторная отправка одного и того же запроса на создание документа, перевода, квитанции или платежа (с тем же ключом запроса) не должна создавать дубликат.
3. Изменение черновика должно выполняться с проверкой версии: если черновик изменён другим пользователем, операция должна отклоняться с кодом 409.
4. Сбой записи в журнал аудита должен отменять всю бизнес-операцию (проведение, нумерацию, изменение остатка).
5. Резервное копирование должно выполняться по расписанию с настраиваемыми периодичностью и сроком хранения (по умолчанию 30 дней).
6. Время восстановления из резервной копии (RTO) — не более 4 часов, допустимая потеря данных (RPO) — не более интервала резервного копирования `[УТОЧНИТЬ У ЗАКАЗЧИКА: приемлемые RTO/RPO]`.

#### 4.1.6. Требования к безопасности

1. Технические средства должны соответствовать общим требованиям электробезопасности; специальных требований не предъявляется.
2. Система не должна выполнять действий, приводящих к потере данных без явного подтверждения пользователя.

#### 4.1.7. Требования к эргономике и технической эстетике

1. Интерфейс должен быть полностью на русском языке.
2. Интерфейс должен корректно отображаться на экранах шириной от 390 пикселей (мобильное устройство) до 1920 пикселей и выше.
3. Должны поддерживаться светлая и тёмная темы; контрастность основного и вторичного текста должна соответствовать уровню AA WCAG 2.2.
4. Каждый экран должен иметь различимые состояния «загрузка», «нет данных», «ошибка»; ошибка отображения одного блока не должна приводить к неработоспособности всего приложения.
5. Фильтры списков (касса, период, поиск, тип, статус, категория, контрагент, сортировка, страница) должны сохраняться в адресной строке, чтобы ссылку можно было передать коллеге.
6. Интерфейс должен быть доступен с клавиатуры (видимый фокус, ссылка «перейти к содержимому», подписи элементов управления).
7. Денежные суммы должны вводиться с разделителем «,» или «.» и отображаться с разделением разрядов.
8. Страница входа должна отображать логотип организации, если он загружен.

#### 4.1.8. Требования к эксплуатации, техническому обслуживанию, ремонту и хранению

1. Система должна разворачиваться одной командой средства оркестрации контейнеров из комплекта поставки.
2. Для администратора должна быть доступна панель состояния Системы (функция Ф-24).
3. Журналы работы сервера должны записываться в структурированном формате (JSON) и храниться не менее 30 дней `[УТОЧНИТЬ У ЗАКАЗЧИКА]`.
4. Резервные копии должны храниться также вне сервера Системы `[УТОЧНИТЬ У ЗАКАЗЧИКА: место внешнего хранения]`.

#### 4.1.9. Требования к защите информации от несанкционированного доступа

1. Доступ к любым данным, кроме логотипа организации для страницы входа и служебной проверки работоспособности, должен предоставляться только аутентифицированным пользователям.
2. Пароль: длина от 10 до 256 символов, обязательно наличие букв и цифр; хранение только в виде стойкого хеша с солью.
3. При первом входе и после сброса пароля пользователь обязан сменить пароль; до смены доступны только функции сеанса.
4. Ключ доступа должен действовать не более 15 минут; ключ обновления — не более 7 дней, храниться в защищённом cookie (Secure, HttpOnly, SameSite=Strict), обновляться при каждом использовании и отзываться при выходе и сбросе пароля. Повторное использование отозванного ключа обновления должно отзывать весь сеанс.
5. После 5 неудачных попыток входа с одного адреса за 15 минут вход должен блокироваться с кодом 429; дополнительно ограничивается частота: не более 15 запросов входа и 20 чувствительных операций в минуту.
6. Время проверки неизвестного логина должно совпадать со временем проверки неверного пароля.
7. Изменение ролей, отзыв доступа к кассе и деактивация пользователя должны действовать немедленно, не дожидаясь истечения ключа доступа.
8. Права пользователя определяются ролями (приложение А) и, для всех ролей кроме администратора, списком назначенных касс. Проверка выполняется на сервере для каждого запроса, содержащего или затрагивающего кассу (в том числе через владельца вложения, аванса, задолженности, квитанции).
9. Должно соблюдаться разделение обязанностей:
   - администратор не выполняет финансовых операций (создание, изменение, удаление и проведение документов, сторно, смены, переводы, приём квитанций, распределение платежей, авансы, инвентаризация) и имеет к финансовым данным доступ только на чтение;
   - согласующий расход не может быть его автором;
   - кассир проводит только собственные черновики.
10. Ответы сервера должны содержать заголовки защиты: политика безопасности содержимого (CSP), запрет встраивания во фреймы, запрет подмены типа содержимого, политика передачи Referer, HSTS.
11. Межсайтовые запросы разрешаются только с заданных адресов клиента; действия, использующие cookie, должны проверять источник запроса.
12. Загружаемые файлы должны проверяться по сигнатуре содержимого (а не по расширению) и отдаваться с заголовком, запрещающим их исполнение в браузере.
13. Сервер приложений должен подключаться к БД под учётной записью с минимально необходимыми правами, отличной от учётной записи, применяющей изменения схемы.
14. Секреты (пароли БД, ключи подписи и шифрования) не должны храниться в системе контроля версий.
15. Выгрузка CSV должна нейтрализовать формулы электронных таблиц в пользовательских данных.

#### 4.1.10. Требования по сохранности информации при авариях

1. Проведённые документы, акты инвентаризации и записи журнала аудита должны быть защищены от изменения и удаления средствами СУБД (независимо от прикладного кода).
2. Резервная копия должна шифроваться (AES-256-GCM, ключ 32 байта, хранимый отдельно от копий), сопровождаться контрольной суммой и манифестом.
3. Должна быть функция проверки целостности копии и функция тестового восстановления в отдельную одноразовую базу данных со сверкой остатков касс, сумм задолженностей и платежей, числа проведённых документов и ссылочной целостности. Рабочая база при этом не должна изменяться.
4. Подмена или повреждение копии должны обнаруживаться и фиксироваться в журнале аудита.

#### 4.1.11. Требования к защите от влияния внешних воздействий

Специальные требования не предъявляются. Сервер должен размещаться в помещении с ограниченным доступом и источником бесперебойного питания `[УТОЧНИТЬ У ЗАКАЗЧИКА]`.

#### 4.1.12. Требования к патентной чистоте

Используемое программное обеспечение должно распространяться по лицензиям, допускающим использование в организации без оплаты либо с оплатой, согласованной с заказчиком. Перечень компонентов и лицензий приводится в документации.

#### 4.1.13. Требования по стандартизации и унификации

1. Документация оформляется с учётом ГОСТ 34.602-2020, ГОСТ 34.201 и методических указаний вуза `[УТОЧНИТЬ У НАУЧНОГО РУКОВОДИТЕЛЯ: методические указания по оформлению ВКР]`.
2. Обмен данными — HTTP/JSON, описание интерфейса — OpenAPI 3.
3. Коды валют — ISO 4217; даты — ISO 8601.
4. Формы первичных кассовых документов — в соответствии с нормативными актами Республики Таджикистан `[УТОЧНИТЬ: утверждённые формы ПКО, РКО, кассовой книги, акта инвентаризации, авансового отчёта]`. До уточнения Система формирует печатные формы, содержащие обязательные реквизиты из раздела 4.2, без заявления о соответствии унифицированным формам.

#### 4.1.14. Дополнительные требования

1. Система не должна включать: складской учёт, учёт товаров, заказов и продаж, банковские платежи и интеграции, электронную подпись, интеграцию с бухгалтерскими программами, CRM, учёт кадров, геолокацию. Контрагент используется только как реквизит документа.
2. Система должна поставляться с набором синтетических демонстрационных данных и пользователей всех ролей для обучения и испытаний.

### 4.2. Требования к функциям (задачам), выполняемым системой

| | |
|---|---|
| Исполнитель | Бухгалтер, кассир |

| Выход | Смена со статусом `open`/`closed`, расчётным и фактическим остатком, разницей (недостача/излишек), пересчётом по купюрам |

Если передан пересчёт по купюрам, сумма «номинал × количество» обязана совпасть с фактическим остатком, иначе 400; пересчёт сохраняется вместе со сменой и не изменяется. Разница «факт − расчёт» сохраняется и отображается в блоке «Требует внимания». Открытие и закрытие фиксируются в аудите |

#### Ф-08. Регистрация кассовых документов (черновики)

| | |
|---|---|
| Исполнитель | Бухгалтер (любой черновик в доступных кассах), кассир (только свой) |
| Вход | Касса, дата, вид (приход/расход), сумма, описание, категория соответствующего направления, контрагент (необязательно), тип документа-основания (необязательно), ключ запроса |
| Выход | Черновик с версией, статусом согласования и списком вложений |
| Правила | Сумма больше 0 и не больше ПН-3, ровно 2 знака точности. Дата не в будущем и не раньше начала учёта кассы. Повторная отправка с тем же ключом и тем же содержимым возвращает тот же черновик; с другим содержимым — 409. Изменение и удаление — только со совпадающей версией. Черновик не влияет на остаток. Любое изменение черновика сбрасывает статус согласования в `none` |

#### Ф-09. Согласование расходов

| | |
|---|---|
| Исполнитель | Отправка — бухгалтер, кассир (свой черновик); решение — руководитель |
| Вход | Отправка: черновик расхода. Согласование: необязательный комментарий. Отклонение: обязательная причина |
| Выход | Статус согласования `none` → `pending` → `approved` / `rejected`; кто и когда принял решение, комментарий; реестр документов на согласовании с фильтром по статусу и кассе |
| Правила | Функция действует, если в настройках задан порог согласования. Расход с суммой не меньше порога можно провести только в статусе `approved`, иначе 409 «Расход требует согласования руководителя». Согласующий не может быть автором документа — 409. Решение принимается только по документу в статусе `pending`. Отклонённый документ можно изменить (статус сбрасывается в `none`) и отправить повторно. Каждое действие фиксируется в аудите. Число документов на согласовании выводится на панели показателей |

#### Ф-10. Проведение кассового документа

| | |
|---|---|
| Исполнитель | Бухгалтер (любой черновик), кассир (только свой) |
| Вход | Идентификатор черновика, подтверждённая пользователем версия |
| Выход | Проведённый документ с номером, моментом проведения, проводившим пользователем, снимком реквизитов |
| Правила | Проведение выполняется атомарно с блокировкой документа, кассы и смены и изоляцией, исключающей одновременное проведение конфликтующих документов. Проверяются: версия; статус `draft`; доступ к кассе; авторство (для кассира); активность кассы; корректность суммы; дата не в будущем и не раньше начала учёта; наличие открытой смены на дату документа; остаток не становится отрицательным ни на одну дату (с учётом более поздних проведённых документов); лимит кассы не превышается; согласование (Ф-09). Номер присваивается по шаблону `ПКО|РКО-<код кассы>-<год>-<шестизначный номер>` со сквозной нумерацией по кассе, виду и году. В документ записываются названия организации, кассы, категории и контрагента на момент проведения, поэтому печатная форма не меняется при переименовании справочников. При конфликте параллельных транзакций пользователь получает 409 с предложением повторить. Проведение фиксируется в аудите |

#### Ф-11. Сторно

| | |
|---|---|
| Исполнитель | Бухгалтер |
| Вход | Проведённый документ, причина (обязательна), дата |
| Выход | Черновик обратного вида на ту же сумму, связанный с оригиналом |

Сумму и кассу сторно изменить нельзя. Остаток меняется только при проведении сторно; после проведения у оригинала фиксируется ссылка на сторно. Оригинал остаётся в журнале без изменений |

#### Ф-12. Межкассовый перевод

| | |
|---|---|
| Исполнитель | Бухгалтер, кассир (при доступе к обеим кассам) |
| Вход | Касса-источник, касса-получатель, дата, сумма, описание, ключ запроса |
| Выход | Запись перевода и два проведённых документа (расход в источнике, приход в получателе) с номерами `ПЕРЕВОД-РКО-…` и `ПЕРЕВОД-ПКО-…` |

### 4.3. Требования к видам обеспечения

#### 4.3.1. Математическое обеспечение

1. Остаток кассы на дату D: `Остаток(D) = НачальныйОстаток + Σ приходов(дата ≤ D) − Σ расходов(дата ≤ D)` по проведённым документам.
2. Допустимость проведения документа с датой D: для всех дат d ≥ D после добавления документа `Остаток(d) ≥ 0` и, если задан лимит, `Остаток(d) ≤ Лимит`. Порядок документов внутри дня определяется последовательностью проведения.
3. Разница смены: `Разница = ФактическийОстаток − РасчётныйОстаток`; `< 0` — недостача, `> 0` — излишек.
4. Пересчёт: `Сумма = Σ (Номинал_i × Количество_i)`.
5. Остаток аванса: `Остаток = СуммаАванса − Σ СуммаСтроки_j`.
6. Пересчёт в базовую валюту: `СуммаTJS = Сумма × Курс(валюта, дата)`, где курс — последний установленный не позднее даты; округление до 2 знаков по банковскому правилу `[УТОЧНИТЬ У ЗАКАЗЧИКА: правило округления]`.
7. Все расчёты выполняются в десятичной арифметике с фиксированной точкой.

#### 4.3.2. Информационное обеспечение

1. Данные хранятся в реляционной СУБД; целостность обеспечивается первичными и внешними ключами, ограничениями уникальности и проверочными ограничениями (допустимые статусы, виды, положительные суммы).
2. Основные информационные объекты: пользователь, роль, сеанс, попытка входа, организация, валюта, курс, номинал, филиал, касса, начальный остаток, доступ к кассе, категория, контрагент, тип документа, кассовый документ, счётчик нумерации, смена, пересчёт по купюрам, перевод, задолженность, распределение платежа, квитанция представителя, аванс, строка авансового отчёта, вложение, акт инвентаризации, запись аудита, отметка уведомления.
3. Проведённые документы, акты инвентаризации и журнал аудита защищаются от изменения на уровне СУБД.
4. Содержимое вложений, логотипа и аватаров хранится в файловом хранилище сервера; в БД хранятся метаданные и контрольная сумма.
5. Изменения структуры БД выполняются только добавлением новых версий схемы; ранее применённые изменения не редактируются.
6. Входные данные поступают от пользователей через формы ввода; выходные — экранные формы, CSV, PDF.

#### 4.3.3. Лингвистическое обеспечение

1. Язык интерфейса, сообщений об ошибках, отчётов и печатных форм — русский.
2. Сумма прописью — на русском языке с наименованием валюты.
3. Коды ролей, статусов и видов в API — латиница (`draft`, `posted`, `pending` и т. п.); в интерфейсе они отображаются русскими названиями.
4. Формат дат в интерфейсе — ДД.ММ.ГГГГ; в API — ГГГГ-ММ-ДД.

## 6. Порядок разработки автоматизированной системы

1. Разработка ведётся итерациями («волнами»); каждая итерация завершается работающей версией, прошедшей автоматические проверки.
2. Исходный код и документация хранятся в системе контроля версий; изменения вносятся через отдельные ветви с проверкой непрерывной интеграцией перед слиянием в основную ветвь.
3. Каждое бизнес-правило сопровождается модульным тестом, каждый сценарий API — интеграционным тестом на реальной СУБД (в изолированной тестовой базе), ключевые пользовательские маршруты — браузерным тестом.
4. Решения, влияющие на архитектуру, фиксируются записями архитектурных решений (ADR).
5. Изменения требований оформляются новой редакцией ТЗ с перечнем изменений и согласуются с заказчиком и научным руководителем.
6. Для разработки и испытаний используются только синтетические данные; реальные данные заказчика используются только в опытной эксплуатации.

8. Внести изменения во внутренние документы организации (положение о кассе, должностные инструкции) с учётом разделения обязанностей `[УТОЧНИТЬ У ЗАКАЗЧИКА]`.
