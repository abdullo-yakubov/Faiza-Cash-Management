## 1. Резюме аудита

Проект — веб-приложение с React 19/Vite 7, ASP.NET Core на .NET 10, EF Core/Npgsql и PostgreSQL. Сервер организован как одно приложение с проектами Domain, Application, Infrastructure, API и отдельным Migrator: это послойное приложение и разумная база для Modular Monolith. Наличие отдельного Domain/Application ещё не доказывает полное соответствие Clean Architecture: в API много маршрутов и сценарной логики, которую следует инвентаризировать до рефакторинга.

Функциональность в коде шире простой кассовой книги: учётные записи/роли, филиалы/кассы/доступы, операции и сторно, смены, переводы, взаиморасчёты и платежи, чеки представителей, dashboard, отчёты PDF/CSV, аудит, уведомления, backup. Это вывод из исходников и миграций, а не заявление об успешной работе функций.

Рабочее дерево содержит незакоммиченные изменения: модифицированные README/API/domain/EF snapshot/frontend/test/seed файлы; новые migration, NotificationCenter и E2E; удалённые отчёты. Аудит их не сбрасывает и не переупорядочивает. `git status` и последние коммиты зафиксированы в рабочем контексте; текущая ветка — `main`. Проверка чистого клона не проводилась.

В текущем этапе сборка и тесты не запускались: результат первого этапа — статический аудит и это ТЗ. `VERIFIED` ниже присваивается только отдельным проверенным доказательствам в исходниках/конфигурации, но не рабочей готовности системы. Runtime, PostgreSQL, браузер, production и восстановление БД не проверялись.

### 3.2 Роли и доступ

Найдены роли `admin`, `accountant`, `cashier`, `manager`, `auditor`. Эндпоинты сочетают `[Authorize(Roles=...)]`, `[Authorize]`, `ICashboxAccess` и middleware. Часть CRUD категорий/контрагентов в `DirectoryEndpoints` использует общий массив `admin, accountant`; область доступа требуется сверить по каждому маршруту. Аудит разрешён admin/accountant/manager/auditor. Для корректной приёмки нужна единая матрица «роль × действие × филиал/касса» и негативные HTTP-тесты по каждой границе доступа.

### 3.3 Сквозной бизнес-процесс (целевой и частично обнаруженный)

Аутентификация → выбор доступного филиала/кассы → открытие смены → создание черновика прихода/расхода → серверная проверка суммы, прав, смены и доступного остатка → атомарное проведение с документным номером → обновление остатка/отчётов → аудит → сверка и закрытие смены. Дополнительные процессы: связанный перевод; создание задолженности и распределение платежа; учёт передачи/приёма денег представителем; отчёты и резервирование.

Система использует одну организационную валюту в UI согласно найденным локальным настройкам/пояснению страниц, однако доменная модель кассы содержит Currency; реальный контракт многовалютности нужно уточнить. Не считать поведение официальным бухгалтерским регламентом без согласования бухгалтерии.

## 4. Выявленные проблемы, риски и неизвестные

1. **Высокий, проверка restore не завершена.** Endpoint уже реализован для отдельной изолированной PostgreSQL и требует ConnectionStrings:BackupRestore; фактическое восстановление и сверка не выполнялись без Docker.
2. **Высокий, архитектурный риск:** API endpoint модули содержат значительный объём сценарной и финансовой логики; публичные маршруты и роли определяются статически и рассредоточены. До реорганизации нужна карта маршрутов и тесты, затем небольшие переносы в Application use cases.
3. **Высокий, проверка безопасности не завершена:** нет результата актуального сквозного security test/ручной проверки production-конфигурации. Статическая проверка headers, CORS и throttling не подтверждает OWASP-соответствие.
4. **Высокий, проверка эксплуатации не завершена:** compose/Docker, TLS через proxy, forwarded headers, секреты, права PostgreSQL, миграции на чистой и обновляемой БД и restore не запускались в этом этапе.
5. **Высокий, Git/управление изменениями:** незакоммиченные изменения включают удалённые отчёты и миграцию/изменения API. Необходимо понять ожидаемый состав релиза и сохранить все рабочие изменения. Аудит их не отменял.
6. **Средний, зависимости:** потенциальное расхождение lock-графа EF Core/Npgsql (см. стек). Требуется проверка restore в locked mode.
7. **Средний, требования:** не обнаружена подтверждённая единая актуальная матрица ролей, критериев приёмки, SLA, retention, RPO/RTO и утверждённых шаблонов документов.
8. **Средний, UX/a11y:** имеются отдельные тесты контраста/UX и семантическая разметка, но нет зафиксированного сквозного WCAG 2.2 AA аудита клавиатуры/скринридера и фактических адаптивных проверок.
9. **Средний, денежная целостность:** имеются decimal(18,2), проверки/constraints, блокировки и concurrency token в отдельных сценариях; системное доказательство конкурентных сценариев по всем видам операций/платежей отсутствует.
10. **Непроверено:** скорость на реалистичных объёмах, восстановление после сбоя, журналирование без утечки чувствительных данных, состояние настоящей БД и production.

Это выявленные пробелы доказательств и/или конкретное отсутствие функции, а не заявление о наличии неизвестных уязвимостей. Полный penetration test не выполнялся.

## 5. Целевая архитектура: Clean Architecture + Modular Monolith

Сохранить развёртывание одним API и одной реляционной БД. Не вводить микросервисы без измеримого требования. Модульный монолит организовать вокруг бизнес-границ:

- **Identity & Access:** пользователи, роли, назначения филиалов/касс, auth.
- **Organization:** филиалы, кассы, валюта и настройки.
- **Cash Operations:** черновики, проводки, сторно, денежный журнал и баланс.
- **Shifts:** открытие, сверка, закрытие.
- **Transfers:** парные движения между кассами.
- **Settlements:** задолженности, платежи, allocation.
- **Representatives:** движение/приём ответственности представителями.
- **Reporting:** dashboard, PDF/CSV.
- **Audit & Notifications:** аудит и уведомления.
- **Backup Operations:** создание, проверка и восстановление по ограниченному операторскому сценарию.

Слои и зависимости:

```text
React UI → ASP.NET Core API → Application use cases → Domain
                                  ↓ ports/interfaces
                              Infrastructure → EF Core/PostgreSQL
```

Domain не зависит от ASP.NET, EF, UI и инфраструктуры. Application владеет сценариями, DTO, валидируемыми командами, авторизационными политиками/портами и транзакционными контрактами. Infrastructure реализует persistence, PDF, email/файловые/backup адаптеры. API отвечает за HTTP, binding, authentication, policy, transport DTO и Problem Details. Модули могут ссылаться на публичные контракты друг друга, не обходя границы через чужие таблицы без явно согласованного read model.

Не создавать абстракцию, слой или библиотеку без конкретной причины. Сначала карту зависимостей и финансовые тесты; затем исправлять границы малыми проверяемыми изменениями. Существующие проекты можно сохранить и развивать инкрементально.

## 6. Инженерные требования к backend

### 6.1 Код и ООП

- **ARCH-01 / P1:** соблюдать направленность зависимостей; доменные правила тестируемы без сети/БД. Приёмка: dependency map/build analysis показывает отсутствие Domain → Infrastructure/API.
- **ARCH-02 / P1:** применять SRP и интерфейсы для внешних границ, а не интерфейс на каждый класс. Приёмка: сценарии операций не смешивают HTTP binding, бизнес-решение, SQL и формат ответа.
- **ARCH-03 / P2:** DRY для общей бизнес-логики, KISS/YAGNI для формы решения. Приёмка: нет дублирующих формул финансовых правил; новые слои обоснованы конкретным сценарием.
- **ARCH-04 / P1:** использовать DI с корректными lifetime; DbContext scoped, не захватывать scoped service singleton-объектом. Приёмка: DI validation и тест старта проходят.
- **ARCH-05 / P1:** I/O-операции async с `CancellationToken`; не блокировать через `.Result`/`.Wait()`. Приёмка: DB/файловые/HTTP пути асинхронны и отменяются.
- **ARCH-06 / P1:** внешние HTTP DTO отделены от EF entities и domain; ошибки представлены единым `ProblemDetails` с correlation id, без stack trace/секретов клиенту.
- **ARCH-07 / P1:** валидация входных данных на сервере и доменные инварианты в Domain/Application; ошибки валидации не приводят к 500.
- **ARCH-08 / P1:** структурированные логи с request/correlation id; секреты, токены, пароли и чувствительные финансовые payload не логируются.

### 6.2 REST API и доступ

- **API-01 / P1:** документировать все маршруты OpenAPI или актуальным API-каталогом: method, path, DTO, success/errors, роль, область доступа, идемпотентность.
- **API-02 / P0:** любой закрытый маршрут защищён явной authorization policy; health endpoint раскрывает только минимум статуса.
- **API-03 / P0:** проверять RBAC и объектный scope (branch/cashbox) на сервере до чтения/изменения данных; запрещать IDOR и доступ по чужому идентификатору.
- **API-04 / P0:** финансовое проведение/перевод/платёж атомарны; повторные команды не создают дубль; конкуренция возвращает определённый conflict.
- **API-05 / P1:** пагинация, сортировка и верхние пределы размера страницы для коллекций; фильтры выполняются БД, не материализуют всю таблицу без ограничения.
- **API-06 / P1:** единые HTTP коды: 400 validation, 401 unauthenticated, 403 forbidden, 404 absent/out-of-scope согласно политике раскрытия, 409 business/concurrency conflict, 429 throttled.
- **API-07 / P1:** CORS разрешает только конфигурируемые front-end origins; cookie и изменяющие запросы защищены от CSRF в соответствии с выбранной auth-схемой.
- **API-08 / P1:** public-facing API имеет ограничения тела запроса, таймауты и rate limits, согласованные с рабочей нагрузкой.

Фактические группы маршрутов, обнаруженные в API: `/api/auth/*`, `/api/users`, `/api/roles`, `/api/branches`, `/api/cashboxes`, `/api/access`, `/api/shifts`, `/api/operations`, `/api/transfers`, `/api/settlements`, `/api/representative-receipts`, `/api/dashboard`, `/api/analytics`, `/api/category-summary`, `/api/reports/*`, `/api/audit/*`, `/api/notifications/*`, `/api/backups/*`, `/health`. Перечень семейств не заменяет полную инвентаризацию параметров/ролей каждого endpoint.

### 6.3 Ошибки и логирование

- Центральная обработка исключений и стабильный JSON-формат ошибок.
- Корреляция UI → API → лог по request id.
- Ожидаемые бизнес-отказы не логировать как необработанные ошибки; системные ошибки логировать с exception и безопасным контекстом.
- Audit — неизменяемая бизнес-история с минимальными необходимыми полями; application logs не подменяют audit trail.
- Ротация, retention и доступ к файлам логов определены конфигурацией эксплуатации.

## 7. Требования к React frontend

- **FE-01 / P1:** поддерживать понятные границы страниц, бизнес-компонентов, общих UI-компонентов, hooks и API-клиента; компоненты представления не обращаются к БД/серверу напрямую.
- **FE-02 / P1:** единый API client: base URL, credentials/token behavior, сериализация, обработка 401/403/409/429 и Problem Details.
- **FE-03 / P1:** hooks управляют локальным и серверным состоянием по простому контракту; не добавлять state-management библиотеку без доказанной сложности.
- **FE-04 / P1:** для загрузки/ошибки/пустого результата/успеха — отдельные состояния; критические действия подтверждаются, ошибки не маскируются фиктивным нулём.
- **FE-05 / P1:** адаптивность для узких экранов и рабочего desktop; таблицы и диалоги не обрезают ключевые действия.
- **FE-06 / P1:** доступность: семантический HTML, label/name, клавиатурный доступ, видимый focus, контраст WCAG 2.2 AA, доступные ошибки и диалоги.
- **FE-07 / P2:** состояние фильтров/ссылок воспроизводимо и не раскрывает секретные параметры; формат дат/денег централизован.
- **FE-08 / P1:** frontend не считается границей безопасности; все права и финансовая валидация повторяются сервером.

## 8. Требования к PostgreSQL и финансовой целостности

- **DB-01 / P0:** денежные суммы — `numeric/decimal` с явной точностью и валютной шкалой; запрещены binary floating point для расчёта денег.
- **DB-02 / P0:** применяются ACID-транзакции для проведения, парных переводов и allocation платежей; rollback проверяется fault-injection тестом.
- **DB-03 / P0:** ограничения PK/FK/unique/check защищают инварианты независимо от UI; для истории — `RESTRICT` либо осознанная политика архивации.
- **DB-04 / P0:** защита от гонок: row lock/optimistic concurrency/unique idempotency key; демонстрация двух конкурирующих запросов даёт ровно один финансовый эффект.
- **DB-05 / P1:** индексы оправданы реальными фильтрами и планами `EXPLAIN`; миграции последовательны, проверяются на пустой БД и на копии предыдущей схемы.
- **DB-06 / P1:** production миграции выполняются отдельным deploy/migrator шагом; приложение production не запускает несанкционированное автоматическое изменение схемы.
- **DB-07 / P1:** DB role runtime least privilege; backup/migrator credentials разделены.
- **DB-08 / P0:** расчёт остатка воспроизводим по упорядоченному журналу; сумма/порядок posting, reversals, shifts, transfers и settlement allocation сверяются с независимым oracle-тестом.
- **DB-09 / P1:** UTC timestamps и явно определённая бизнес-дата/часовой пояс; правила перехода даты задокументированы.
- **DB-10 / P1:** архив миграций не переписывается после применения; обратимость/безопасность rollback описана для каждой миграции.

Имеющиеся признаки в коде: decimal precision 18,2; check constraints сумм и состояний; уникальные ключи запросов/номеров; concurrency token; row-level `FOR UPDATE` и транзакции в некоторых сценариях. Они подтверждают наличие отдельных мер, но не полноту для всех финансовых маршрутов.

## 9. Безопасность

- **SEC-01 / P0:** проверка OWASP Top 10 и ASVS подходящего уровня для auth, access control, injection, cryptographic failures, misconfiguration, logging, SSRF/dependencies.
- **SEC-02 / P0:** JWT подписываются сильным секретом из secret store/environment; validate issuer/audience/signature/lifetime; короткий access lifetime и отзыв/ротация refresh token.
- **SEC-03 / P0:** credential storage использует признанный password hashing алгоритм с salt и work factor; reset/смена пароля инвалидируют активные refresh-сессии.
- **SEC-04 / P0:** HTTPS в рабочей среде, secure/HttpOnly/SameSite cookies, доверие forwarded headers только от известных proxy IP.
- **SEC-05 / P0:** секреты исключены из Git, логов, образов, архивов и примеров; проверить историю Git и доступы без публикации секретных значений.
- **SEC-06 / P0:** CSRF, CORS, XSS, CSP, clickjacking и безопасная загрузка/экспорт файлов проверяются тестами.
- **SEC-07 / P0:** rate limiting login и иных чувствительных операций, без возможности простого обхода через spoofable forwarded headers.
- **SEC-08 / P0:** аудит админских и финансовых действий; исключение секретов и контроль доступа к audit.
- **SEC-09 / P0:** backup зашифрован при передаче/хранении, доступ ограничен, целостность проверена; restore выполняется только в явно выбранную целевую БД после защитных preflight-проверок.
- **SEC-10 / P1:** dependency audit/SCA, обновления и SBOM либо воспроизводимый пакетный список; критические/high проблемы рассмотрены до релиза.
- **SEC-11 / P1:** threat model для ролей, границ филиал/касса, backup, экспорта и действий администратора.

Безопасное восстановление не должно незаметно перезаписывать production. Test restore обязан использовать выделенную пустую изолированную БД; production restore — отдельная процедура с подтверждаемой операторской авторизацией, проверкой назначения и аудитом.

Unit и frontend проверки успешны. Критерии P0 финансовой конкурентности/HTTP RBAC/реальной PostgreSQL/restore всё ещё не проверены в этой среде. ## 17. Уточнение целевой архитектуры

Архитектурная цель — **Clean Architecture + Modular Monolith** с текущими backend-проектами Domain, Application, Infrastructure, API и Migrator. Приложение разворачивается одним API с PostgreSQL; микросервисы не вводятся. Domain не зависит от ASP.NET Core, EF Core, React или Infrastructure. Application содержит сценарии, DTO, валидацию и контракты; Infrastructure реализует контракты persistence/PDF/backup/logging; API отвечает за HTTP, auth/policies, ProblemDetails и DI composition root. Модули взаимодействуют через контракты и не обходят бизнес-инварианты друг друга.

Перенос сценариев из API выполняется только небольшими изменениями после определения правила и регрессионного теста. Не требуется внедрять все GoF-паттерны, интерфейс на каждый класс, Repository/UoW поверх EF без причины либо CQRS там, где достаточно простого use case.

## 19. Финансовые инварианты P0

Каждый инвариант подтверждается интеграционными тестами на PostgreSQL; unit-тесты остаются дополнительным уровнем.

1. Суммы используют decimal/numeric, не `float`/`double`.
2. Черновик не меняет баланс.
3. Проведение имеет ровно один финансовый эффект.
4. Повтор команды с тем же idempotency key не создаёт дубль.
5. Перевод выполняется полностью или полностью откатывается.
6. Закрытая смена запрещает неразрешённые изменения.
7. Платёж не превышает долг без явно утверждённого правила.
8. Сторно сохраняет исходную запись и причину.
9. Dashboard и отчёты совпадают с ledger при одинаковых фильтрах.
10. Конкурентные запросы не создают двойное списание/зачисление.

Минимальные PostgreSQL сценарии: два параллельных расхода, повторное проведение, одновременная оплата долга, ошибка между сторонами перевода, rollback, политика отрицательного остатка и повтор idempotency key. Уже применённые миграции не переписывать; миграции проверять на пустой изолированной БД и на копии предыдущей схемы.

## 22. Приёмка и статусы

На каждое требование реестра указывать реализацию, доказательство (точный путь/команда/результат), статус и приоритет. Допустимые статусы: `VERIFIED`, `PARTIAL`, `MISSING`, `FAILED`, `BLOCKED`. `VERIFIED` означает, что критерий конкретно подтверждён проверкой; наличие исходного файла или успешная сборка недостаточны. Невыполненная проверка обозначается `NOT RUN` в журнале выполнения и не трактуется как PASS.

Условия `READY FOR DIPLOMA DEMONSTRATION`: все P0 финансовые и авторизационные критерии проверены, миграции применены на чистой тестовой БД, unit/integration/security/E2E пройдены, backup реально восстановлен изолированно, нет нерешённых Critical/High security findings, чистый запуск воспроизводим, документы согласованы с фактическим поведением. Иначе итог `NOT READY` с причинами и ограничениями.

## 25. Реализация замечаний аудита (23.11.2026)

- Задолженности теперь имеют nullable `CashboxId` с миграцией `SettlementCashboxScope`; новые записи требуют выбора доступной активной кассы. Список задолженностей, история, PDF/JSON отчёты, Dashboard, сводка и уведомления фильтруются по кассовому scope пользователя. Для исторических записей без кассы сохранён доступ администратора; автоматическое назначение не выполняется, потому что исходная касса неизвестна.
- Платёж должен быть в той же валюте, что и касса долга. Добавлены security regression cases на список/историю/отчёт по чужой кассе.
- Отметить уведомление прочитанным можно только пока оно действительно доступно пользователю; повторные одновременные отметки обрабатываются через `ON CONFLICT DO NOTHING`.
- Успешное тестовое восстановление резервной копии записывается в бизнес-аудит. ТЗ v1.1 и предыдущие статусы restore приведены в соответствие с кодом.
- Сброс пароля администратором уже служит контролируемым восстановлением: отзывает refresh-сессии и требует смену временного пароля при входе. Self-service reset по email/телефону не добавлен: в проекте не настроен проверенный канал подтверждения личности.

**Остаётся выполнить в среде с disposable PostgreSQL/Docker:** применить новую миграцию на чистой и upgrade базе; выполнить security/integration сценарии и фактическую restore reconciliation. Также остаются ручные/организационные работы: утвердить RBAC/денежные правила/retention/RPO/RTO, провести WCAG keyboard/screen-reader review, нагрузочный прогон и smoke чистого production deployment. Эти пункты нельзя закрыть изменением исходников или успешной компиляцией.
