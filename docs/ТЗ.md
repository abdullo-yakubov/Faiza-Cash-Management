## 1. Общие сведения

### 1.1. Наименование системы
Полное наименование — «Система кассового учёта ООО „Фаиза“». Краткое — **FAIZA GOLD** (в коде — `FaizaCash`).

### 1.2. Заказчик и разработчик
Заказчик — бухгалтерия ООО «Фаиза» (Республика Таджикистан). Разработчик — студент 4 курса, автор дипломной работы.

### 1.3. Основание и сроки
Основание — задание на выпускную квалификационную работу. Разработка: ноябрь 2026 г. Первая миграция БД — 12.11.2026, последняя — 24.11.2026.

### 1.4. Термины

| Термин | Значение |
|---|---|
| Филиал | Подразделение организации в определённом городе (Душанбе, Худжанд, Бохтар). |
| Касса | Место хранения наличных в одной валюте, принадлежит филиалу. Может иметь лимит остатка. |
| Начальный остаток | Сумма в кассе на дату начала учёта. Задаётся администратором один раз. |
| Смена | Рабочий день кассы. Открывается с расчётным остатком, закрывается с фактическим. Разница фиксируется как недостача или излишек. |
| ПКО / РКО | Приходный / расходный кассовый ордер. |
| Черновик (`draft`) | Документ, который ещё не влияет на остаток и может быть изменён или удалён. |
| Проведение (`posted`) | Документ получает номер и меняет остаток. После этого изменить или удалить его нельзя. |
| Сторно | Обратный документ с указанием причины, отменяющий проведённую операцию. Оригинал остаётся в журнале. |
| Межкассовый перевод | Пара проведённых документов: РКО в кассе-источнике и ПКО в кассе-получателе. |
| Задолженность | Дебиторская (`receivable`) или кредиторская (`payable`) задолженность контрагента. Погашается проведёнными платежами. |
| Торговый представитель | Сотрудник, который собирает наличные у клиентов и сдаёт их в кассу по квитанции. |
| Доступ к кассе | Отдельное от роли разрешение пользователю работать с конкретной кассой. |

## 2. Назначение и цели

### 2.1. Назначение
Система ведёт единый журнал наличных денежных движений организации: приходные и расходные документы, смены, переводы между кассами, задолженности контрагентов, квитанции торговых представителей. Система также формирует отчёты и ведёт журнал аудита.

### 2.2. Цели автоматизации
1. Заменить ручное ведение кассовой книги электронным журналом с автоматической нумерацией документов.
2. Исключить отрицательный остаток и превышение лимита кассы на уровне сервера.
3. Обеспечить неизменяемость проведённых документов и журнала аудита на уровне БД.
4. Разграничить права по ролям и по конкретным кассам.
5. Получать отчёты (кассовая книга, смены, филиалы, переводы, задолженности, представители) в CSV и PDF.
6. Обеспечить резервное копирование с шифрованием и проверкой восстановления.

### 2.3. Границы системы
В объём **не входят**: склад, товары, заказы и продажи как самостоятельные процессы, банковские платежи и интеграции, электронная подпись, интеграция с бухгалтерскими программами, CRM, HR, GPS. Контрагент используется только как реквизит документа. Соответствие официальным унифицированным формам не заявляется.

## 4. Функциональные требования

### ФТ-01. Аутентификация и сеанс
- Вход по логину и паролю. Access-токен JWT живёт 15 минут. Refresh-токен живёт 7 дней, хранится в cookie, ротируется при обновлении и отзывается при выходе.
- После 5 неудачных попыток с одного IP за 15 минут вход блокируется (HTTP 429). Дополнительно действует ограничение частоты: 15 запросов в минуту на вход, 20 в минуту на чувствительные операции.
- Неизвестный логин проверяется так же долго, как неверный пароль. Это защищает от перебора логинов.
- Пароль: от 10 до 256 символов, обязательно буквы и цифры. Хранится как хеш PBKDF2 с солью.
- При первом входе пользователь обязан сменить пароль. До смены доступны только `/api/auth/*`.
- Изменение ролей или деактивация пользователя действуют сразу, не дожидаясь истечения JWT.

### ФТ-02. Пользователи и доступ
- Администратор создаёт пользователей, редактирует ФИО, роли, активность и сбрасывает пароль.
- Администратор выдаёт и отзывает доступ пользователя к кассе.

### ФТ-03. Организация, филиалы, кассы
- Настройки организации: название, валюта (TJS), часовой пояс (Asia/Dushanbe).
- Филиалы: код, название, город, активность.
- Касса: код, название, филиал, валюта, необязательный лимит остатка, активность.
- Начальный остаток задаётся один раз и только до первой смены и первого проведённого документа.

### ФТ-04. Справочники
- Категории прихода и расхода (иерархия через `ParentId`), архивирование.
- Контрагенты: название, вид, ИНН, контакт, активность.
- Типы документов-оснований.

### ФТ-05. Кассовые смены
- У кассы может быть только одна открытая смена.
- При открытии смены остаток должен совпадать с расчётным. При несовпадении сервер возвращает 409 и расчётную сумму.
- При закрытии вводится фактический остаток. Система сохраняет разницу `факт − расчёт` (недостача или излишек).
- Документ можно провести только в открытую смену на дату документа.

### ФТ-06. Кассовые документы (черновики)
- Создание прихода или расхода: дата, сумма, описание, категория, контрагент, тип основания.
- Сумма: больше 0, не больше 9 999 999 999 999 999,99, точность 2 знака.
- Черновик можно изменить или удалить с проверкой версии (оптимистическая блокировка).
- Повторная отправка с тем же `RequestKey` не создаёт дубль (идемпотентность).

### ФТ-07. Проведение
- Выполняется в транзакции `Serializable` с блокировкой строк операции, кассы и смены.
- Проверки: доступ к кассе, кассир проводит только свой черновик, касса активна, дата не в будущем и не раньше начального остатка, смена открыта, остаток не станет отрицательным ни на одну дату, лимит кассы не превышен.
- Номер присваивается по шаблону `ПКО|РКО-<код кассы>-<год>-<000001>` с отдельной нумерацией по кассе, типу и году.
- При проведении в документ записываются названия организации, кассы, категории и контрагента. Поэтому печатная форма не меняется после переименования справочников.

### ФТ-08. Сторно
- Сторнировать можно только проведённый документ, который сам не является сторно и ещё не сторнирован.
- Сторно создаётся как черновик обратного типа на ту же сумму с обязательной причиной. Дата — не раньше оригинала и не позже сегодняшней.
- Остаток меняется только при проведении сторно. У оригинала при этом заполняется `ReversalId`.

### ФТ-09. Межкассовый перевод
- Источник и получатель — разные кассы. Проверяются остаток источника и лимит получателя.
- Атомарно создаются два проведённых документа (`ПЕРЕВОД-РКО-…` и `ПЕРЕВОД-ПКО-…`), связанные с записью перевода.

### ФТ-10. Задолженности и платежи
- Задолженность: контрагент, направление, основание (`order`, `delivery`, `return`, `manual`), сумма, срок, необязательные касса и представитель.
- Статусы: `open` → `partially_paid` → `paid`, а также `cancelled`.
- Платёж распределяется только из проведённой операции того же контрагента и соответствующего направления (приход для дебиторской, расход для кредиторской задолженности). Валюты должны совпадать. Распределённая сумма не может превышать ни остаток долга, ни нераспределённую сумму операции.
- История оплат доступна по каждой задолженности. Просроченные задолженности выделяются.

### ФТ-11. Квитанции торговых представителей
- Жизненный цикл: `collected` (собрано) → `handed_over` (передано в кассу) → `accepted` (принято кассиром). Возможна отмена (`cancelled`).

### ФТ-12. Обзор, dashboard и уведомления
- Обзор и dashboard: остатки касс, приход и расход за неделю и месяц, аналитика по категориям, блок «Требует внимания» (расхождения смен за 14 дней, просроченные долги, черновики).
- Центр уведомлений с отметкой «прочитано» для каждого пользователя отдельно.

### ФТ-13. Отчёты

| Отчёт | Экран | CSV | PDF |
|---|:-:|:-:|:-:|
| Кассовая книга (по кассе за период) | ✓ | ✓ | ✓ |
| Печатная форма документа | — | — | ✓ |
| По филиалу | — | ✓ | ✓ |
| Смены | ✓ | ✓ | ✓ |
| Межкассовые переводы | — | ✓ | ✓ |
| Задолженности | ✓ | ✓ | ✓ |
| Торговые представители | ✓ | ✓ | ✓ |

PDF формируются библиотекой QuestPDF. Сумма прописью выводится на русском языке.

### ФТ-14. Журнал аудита
- Фиксируются вход, изменения пользователей, касс, доступов, смен, документов, задолженностей, квитанций и резервных копий.
- Запись в журнал только добавляется. UPDATE и DELETE запрещены триггером БД.
- Есть фильтры по действию, сущности, пользователю и периоду, а также режим технических событий.

### ФТ-15. Резервное копирование
- Ручное и плановое копирование (`Backups:IntervalHours`) через `pg_dump`. Срок хранения задаётся параметром `Backups:RetentionDays` (по умолчанию 30 дней).
- Шифрование AES-256-GCM (в production обязательно), контрольная сумма и манифест.
- «Проверить» сверяет целостность. «Тест восстановления» разворачивает копию в отдельную одноразовую БД, сверяет остатки, суммы долгов и платежей, число документов и внешние ключи, затем очищает эту БД. Рабочая база не перезаписывается.

## 6. Нефункциональные требования

### 6.1. Архитектура
```
Браузер (React 19 + Vite 7)
   │ HTTPS, JSON, Bearer JWT + refresh-cookie
   ▼
nginx / Caddy (TLS, проксирование /api)
   ▼
ASP.NET Core 10 Minimal API
   ├─ Middleware: Request → Auth → RateLimit → Access → DirectoryCache
   ├─ Application: правила (BalanceRules, ShiftRules, ReversalRules), DTO, интерфейсы
   ├─ Infrastructure: EF Core / Npgsql, LedgerService, BackupService, PdfReport
   ▼
PostgreSQL 18 (триггеры неизменяемости)
```
Слои Clean Architecture: `Domain` → `Application` → `Infrastructure` → `Api`. Отдельный проект `Migrator` применяет миграции в production.

### 6.2. Целостность данных
- Деньги хранятся в `decimal` и передаются в JSON строкой (`DecimalStringConverter`), чтобы не терять точность.
- Проведённые документы и аудит защищены триггерами PostgreSQL.
- Конкурентные операции защищены блокировками `FOR UPDATE`, транзакциями `Serializable`, advisory-блокировками и проверкой версии.
- Даты считаются в часовом поясе `Asia/Dushanbe`.

### 6.3. Безопасность
- В production обязательны: `Secure` cookie, ключ шифрования копий, доверенные прокси, HTTPS/HSTS. API не запускается, если есть неприменённые миграции.
- Заголовки ответа: CSP, `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy`.
- CORS разрешён только для заданных origin. Размер тела запроса ограничен 6 МБ.
- Секреты (`.env`, `.runtime/local.json`, `.runtime/demo-users.json`) не попадают в Git.
- Для работы API в production используется отдельная роль PostgreSQL с минимальными правами (`deploy/provision-runtime-role.sql`).

### 6.4. Журналирование
JSON в консоль и в файлы `.jsonl` (`Logs:Directory`).

### 6.5. Производительность
Списки выдаются постранично (`page`, `pageSize`). Справочники кэшируются в памяти. Нагрузочный read-only тест — `tests/load-readonly.mjs`.

## 10. Развёртывание

- **Локально (Windows):** `node scripts/configure-local.mjs` → `node scripts/run-local.mjs` → `npm --prefix frontend run dev`.

## 11. Контроль и приёмка

Полный прогон: `node tests/run-all.mjs`.

| Уровень | Набор | Что проверяет |
|---|---|---|
| Unit (xUnit) | `backend/tests/FaizaCash.UnitTests` | Money, BalanceRules, ShiftRules, шифрование копий, refresh-cookie, сумма прописью |
| Frontend | `frontend/tests/*.test.js` | API-клиент, рендер, UX, контраст, заголовки, демо-режим |
| API + PostgreSQL | `tests/integration.mjs`, `catalog.mjs`, `ledger-integrity.mjs`, `security.mjs` | Сценарии, справочники, целостность журнала, безопасность |
| Приоритетные сценарии | `tests/integration/p0.mjs`, `p1.mjs`, `p2.mjs`, `invariants.mjs` | Критичные бизнес-правила и инварианты |
| Восстановление | `tests/integration/restore.mjs` | Два восстановления подряд в изолированный контейнер |
| E2E | `tests/e2e.mjs` (Playwright) | Браузерный маршрут пользователя |
| CI | `.github/workflows/verify.yml` | restore, build, test, frontend test/build, `npm audit` |

**Критерии приёмки:**
1. `node tests/run-all.mjs` завершается строкой `All suites passed.`
2. Сценарий защиты из README (8 минут) выполняется на демо-данных без ошибок.
3. Проведённый документ и запись аудита нельзя изменить даже прямым SQL-запросом.
4. Тест восстановления копии проходит успешно.

## 12. Известные ограничения и открытые вопросы

1. Администратор может проводить финансовые операции — разделение обязанностей не соблюдено. Это требует решения заказчика.
2. В форме создания пользователя в интерфейсе нет ролей `manager` и `auditor` (они назначаются через API или скрипт).
3. Большая часть логики находится прямо в endpoint-ах (`ApiEndpoints.cs` ~89 КБ), отдельного слоя repository или validator нет.
4. README ссылается на `docs/TESTING.md`, но такого файла нет.
5. В `backend/src/FaizaCash.Api/` лежит временный файл `*.tmp`, его нужно удалить.
6. Production с TLS на реальном домене автоматическими тестами не проверяется.
7. Межкассовый перевод использует первую активную категорию прихода и расхода. Отдельной категории для переводов нет.
