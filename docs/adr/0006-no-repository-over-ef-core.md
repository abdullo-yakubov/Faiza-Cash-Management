# ADR-0006. Отказ от слоя Repository поверх EF Core

**Статус:** принято, реализовано.

## Контекст

Классическая «чистая архитектура» часто предполагает интерфейсы `IRepository<T>` и `IUnitOfWork` между бизнес-логикой и ORM. EF Core уже реализует эти паттерны: `DbSet<T>` — репозиторий, `DbContext` — единица работы. Ключевые операции системы требуют возможностей, которые общий репозиторий скрывает: `SELECT ... FOR UPDATE` через `FromSqlInterpolated`, явные транзакции уровня Serializable, проекции для отчётов, advisory-блокировки.

## Решение

- Обработчики и сервисы работают с контекстом БД напрямую.
- Повторно используемые запросы оформляются как методы-расширения или проекции (`Projections`), а не как репозитории.
- Бизнес-правила, не зависящие от хранения (остаток, смена, сторно, деньги), вынесены в чистые функции слоя Application и покрыты модульными тестами без БД.
- Поведение с реальной БД (блокировки, триггеры, транзакции) проверяется интеграционными тестами на PostgreSQL, а не моками.

## Последствия

- (+) Меньше кода и слоёв; блокировки и транзакции видны там, где они нужны.
- (+) Тесты проверяют реальное поведение PostgreSQL (сериализация, триггеры), которое моки репозитория не воспроизвели бы.
- (−) Слой Api зависит от Infrastructure (EF Core) напрямую; замена ORM потребовала бы правок обработчиков. Для дипломной системы это осознанный компромисс.
- (−) Модульные тесты обработчиков без БД невозможны — компенсируется интеграционными наборами на одноразовой базе `_test`.

## Альтернативы

1. **Generic Repository + Unit of Work** — дублирует EF Core и мешает использовать `FOR UPDATE`/сырые SQL. Отклонено.
2. **Специализированные репозитории на агрегат** — оправданы при нескольких источниках данных; здесь источник один.
3. **Dapper вместо EF Core** — больше контроля над SQL, но нет миграций и отслеживания изменений.
