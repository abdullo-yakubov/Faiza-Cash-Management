# ADR-0001. Неизменяемый журнал на триггерах БД

**Статус:** принято, реализовано (миграция `ImmutableLedger`, 12.11.2026).

## Контекст

Кассовый учёт требует, чтобы проведённый документ и след действий пользователей нельзя было исправить задним числом. Проверка только в коде API не защищает от: ошибки в новом обработчике, прямого SQL-запроса администратора БД, скрипта миграции данных, будущего второго приложения на той же базе. Для дипломной работы важно и показать комиссии гарантию, которую нельзя обойти «через интерфейс».

## Решение

Защищать данные на уровне PostgreSQL триггерами `BEFORE UPDATE OR DELETE`:

- `audit_immutable` на `AuditEvents` — любой `UPDATE`/`DELETE` вызывает исключение «Audit is append-only»;
- `posted_immutable` на `Operations` — если `OLD.Status = 'posted'`, удаление запрещено, а изменение разрешено только для полей `ReversalId` и `Version` (связь со сторно). Сравнение выполняется через `to_jsonb(NEW) - ... IS DISTINCT FROM to_jsonb(OLD) - ...`, поэтому новые столбцы автоматически попадают под защиту.

Прикладной код дополнительно проверяет статус и возвращает пользователю понятную ошибку 403/409 — триггер является последней линией обороны. В волне 1 тот же подход применяется к актам инвентаризации.

## Последствия

- (+) Гарантия держится независимо от прикладного кода; проверяется тестом и ручным SQL на защите.
- (+) Новые поля документа защищены без изменения триггера.
- (−) Исправление ошибки в проведённом документе возможно только сторно (ADR-0002); «тихо поправить» данные нельзя даже администратору.
- (−) Нельзя удалить тестовые данные из рабочей базы; для тестов используется отдельная база `_test`, схема которой пересоздаётся.
- (−) Владелец таблиц может отключить триггер (`ALTER TABLE ... DISABLE TRIGGER`). Поэтому API работает под отдельной ролью без прав владельца (`provision-runtime-role.sql`).
- Миграции не редактируются задним числом: изменение логики триггера — только новой миграцией.

## Альтернативы

1. **Только проверки в коде** — проще, но не защищает от прямого доступа к БД. Отклонено.
2. **Отзыв прав `UPDATE/DELETE` у роли приложения** — не работает: черновики должны изменяться в той же таблице.
3. **Отдельная таблица проведённых документов (event store)** — сильнее изолирует, но удваивает модель и запросы отчётов. Избыточно для объёма дипломной системы.
4. **Хеш-цепочка записей аудита** — обнаруживает, но не предотвращает изменения; может быть добавлена в будущем как дополнение.
