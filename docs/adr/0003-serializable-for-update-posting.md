# ADR-0003. Serializable + FOR UPDATE при проведении

**Статус:** принято, реализовано.

## Контекст

С одной кассой одновременно могут работать кассир и бухгалтер. Классическая гонка: в кассе 100 сомони, два пользователя одновременно проводят расходы по 80. Каждая транзакция по отдельности видит остаток 100 и проходит проверку — итог −60. Аналогично возможны двойное проведение одного черновика, дубли номеров и проведение в смену, которую в тот же момент закрывают.

## Решение

Проведение выполняется в одной транзакции уровня **Serializable**, внутри которой строки блокируются явно и в фиксированном порядке:

1. `SELECT ... FOR UPDATE` документа → проверка `Version` и статуса;
2. `SELECT ... FOR UPDATE` кассы — сериализует все проведения по одной кассе;
3. повторная проверка статуса и доступа после получения блокировки;
4. `SELECT ... FOR UPDATE` смены на дату документа;
5. расчёт остатка по всем проведённым документам и проверка правил;
6. увеличение счётчика номеров, запись документа, запись аудита, `COMMIT`.

Ошибка сериализации PostgreSQL (`40001`) превращается в 409 «Проведение конфликтует с другой транзакцией. Повторите попытку». Межкассовый перевод блокирует обе кассы и обе смены в порядке возрастания идентификатора, чтобы исключить взаимную блокировку. Справочники защищаются от одновременного создания дублей advisory-блокировками.

## Последствия

- (+) Инвариант «остаток ≥ 0 на любую дату» сохраняется при любой конкуренции — подтверждено тестами с параллельными запросами (ровно один 200 и один 409).
- (+) Номера документов без пропусков и дублей: счётчик меняется в той же транзакции.
- (−) Проведения по одной кассе выполняются последовательно; при объёме касс ООО «Фаиза» `[УТОЧНИТЬ У ЗАКАЗЧИКА: объём документов]` это не узкое место.
- (−) Пользователь иногда получает 409 и должен повторить действие; клиент показывает понятное сообщение.

## Альтернативы

1. **Read Committed без блокировок** — допускает отрицательный остаток. Отклонено.
2. **Только `FOR UPDATE` кассы на Read Committed** — достаточно для большинства случаев, но Serializable дополнительно ловит фантомы (новые документы задним числом) без ручного анализа всех путей.
3. **Оптимистическая блокировка через версию кассы** — больше повторов при нагрузке и сложнее в переводах между двумя кассами.
4. **Хранимая процедура проведения в PostgreSQL** — переносит бизнес-правила из тестируемого C# в PL/pgSQL; хуже для сопровождения.
