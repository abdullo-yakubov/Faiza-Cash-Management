# ADR-0008. Вложения на диске, метаданные в БД

**Статус:** принято, реализуется в волне 1.

## Контекст

Волна 1 добавляет сканы и фото первичных документов (до 5 МБ, до 10 файлов на документ), логотип и аватары. Нужно выбрать место хранения содержимого так, чтобы: не раздувать базу и её резервные копии, сохранить связь файла с документом и правами кассы, обнаруживать подмену файла, не открыть путь к исполнению загруженного содержимого.

## Решение

- **Содержимое** файла сохраняется в каталог файлового хранилища сервера (отдельный том контейнера) под именем, сгенерированным системой (идентификатор GUID), без использования имени пользователя в пути.
- **Метаданные** — в таблице БД: владелец (`ownerType`, `ownerId`), исходное имя (очищенное), тип содержимого, размер, SHA-256, кто и когда загрузил.
- Тип определяется по сигнатуре (магическим байтам): JPEG, PNG, WebP, PDF; расширение и `Content-Type` клиента игнорируются.
- Файл отдаётся только через API после проверки доступа к кассе владельца, с `Content-Type` из метаданных, `Content-Disposition` и `X-Content-Type-Options: nosniff`.
- Запись в файл и в БД: сначала файл во временное имя, затем строка в БД в транзакции, затем переименование; осиротевшие файлы удаляются фоновой очисткой.
- Удаление разрешено только пока владелец не проведён / не принят; после этого вложение неизменяемо, как и документ.
- Резервное копирование должно охватывать каталог вложений (архив с тем же шифрованием) — согласовать с реализацией копий.

## Последствия

- (+) База и `pg_dump` остаются компактными; потоковая отдача больших файлов не нагружает СУБД.
- (+) SHA-256 позволяет проверить целостность файла и обнаружить подмену на диске.
- (+) Объём хранилища выводится на панель состояния администратора.
- (−) Два источника данных: возможны рассогласования (строка без файла, файл без строки) — нужна проверка целостности и очистка.
- (−) Резервная копия БД без каталога вложений неполна; тест восстановления должен это учитывать.
- (−) При горизонтальном масштабировании нужен общий том или объектное хранилище.

## Альтернативы

1. **`bytea` в PostgreSQL** — транзакционно и просто копировать, но раздувает базу, копии и время восстановления; ограничение 6 МБ на запрос позволяет, но не масштабируется. Отклонено для вложений; допустимо для логотипа и аватаров (≤ 1 МБ), если реализации так проще.
2. **Large Objects PostgreSQL** — сложнее в сопровождении и правах.
3. **Объектное хранилище (S3/MinIO)** — лучший вариант для масштабирования, но добавляет сервис в развёртывание; можно перейти позже, сохранив метаданные.
