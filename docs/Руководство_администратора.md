# Руководство администратора FAIZA GOLD

Для администратора системы: установка, production-развёртывание, пользователи, резервное копирование и восстановление, ротация ключей, обслуживание. Работа с финансовыми документами администратору недоступна (разделение обязанностей, ADR-0007).

---

## 1. Состав системы

| Компонент | Назначение |
|---|---|
| `db` | PostgreSQL 18.3 — рабочая база `faiza_cash` |
| `migrate` | Одноразовый контейнер: применяет изменения схемы под ролью `faiza_migrator` |
| `provision-runtime` | Одноразовый контейнер: создаёт/обновляет роль `faiza_runtime` с минимальными правами |
| `api` | Сервер приложений (ASP.NET Core), работает под ролью `faiza_runtime` |
| `backup-restore-db` | Одноразовая база на `tmpfs` для теста восстановления копий |
| `frontend` | nginx со статическими файлами клиента |
| `proxy` | Caddy — TLS-сертификат и проксирование `/api` |

Схема — `docs/diagrams/architecture.md`.

## 2. Требования к серверу

- Linux с Docker Engine и Docker Compose v2 (или Windows с Docker Desktop для демонстрации).
- 2 ядра, 4 ГБ ОЗУ, 40 ГБ SSD + место под копии и вложения.
- Публичное DNS-имя, указывающее на сервер; открыты порты 80 и 443 (нужны Caddy для выпуска сертификата Let's Encrypt).

## 3. Установка (production)

1. Склонируйте репозиторий на сервер.
2. Создайте файл `.env` рядом с `docker-compose.production.yml` (права `600`, владелец — администратор). Обязательные переменные:

| Переменная | Значение |
|---|---|
| `FAIZA_DOMAIN` | DNS-имя, например `cash.example.tj` |
| `MIGRATION_DB_PASSWORD` | Пароль роли `faiza_migrator` (только для развёртывания) |
| `RUNTIME_DB_PASSWORD` | Пароль роли `faiza_runtime` (отличается от предыдущего) |
| `BACKUP_RESTORE_DB_PASSWORD` | Пароль одноразовой базы восстановления |
| `BACKUPS__ENCRYPTIONKEY` | Ключ шифрования копий: base64 от 32 случайных байт |
| `JWT__KEY` | Ключ подписи токенов, не менее 32 символов |
| `SEED__ADMINLOGIN` | Логин первого администратора (по умолчанию `admin`) |
| `SEED__ADMINPASSWORD` | Начальный пароль администратора (сменить при первом входе) |

Генерация случайных значений:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"   # ключ копий
openssl rand -base64 48                                                       # JWT и пароли
```

3. **Сохраните копию `BACKUPS__ENCRYPTIONKEY` вне сервера** (сейф, менеджер паролей заказчика). Без ключа зашифрованные копии восстановить невозможно.
4. Запуск:

```bash
docker compose -f docker-compose.production.yml up --build -d
docker compose -f docker-compose.production.yml ps
```

Порядок старта: `db` → `migrate` → `provision-runtime` → `api` → `frontend`, `proxy`. API не запустится, если есть неприменённые миграции, не задан ключ копий, не включён Secure-cookie или не настроены доверенные прокси — это защитные проверки, их нельзя отключать.

5. Откройте `https://<FAIZA_DOMAIN>`, войдите под `SEED__ADMINLOGIN` и смените пароль.
6. **Включите плановое резервное копирование** (см. п. 6.1) — по умолчанию оно выключено.

### Демонстрационная установка

`docker compose up --build -d` с файлом `.env` по `.env.example`; frontend — http://localhost:8085, API — http://localhost:5085. Используется только для учебных данных.

## 4. Первоначальная настройка

Выполняется администратором в интерфейсе в таком порядке:

1. **Настройки организации**: наименование, валюта (TJS), часовой пояс (Asia/Dushanbe), порог согласования расходов (W1), логотип (W1, PNG/JPEG/WebP до 1 МБ).
2. **Филиалы**: код, название, город.
3. **Кассы**: код, название, филиал, валюта, лимит остатка.
4. **Справочники** (можно поручить бухгалтеру): категории прихода и расхода, контрагенты (сотрудники-подотчётные лица — вид «сотрудник»), типы документов-оснований.
5. **Номиналы купюр** (W1): проверить справочник сомони/дирамов по данным НБТ.
6. **Курсы валют** (W1), если есть кассы не в TJS.
7. **Пользователи** (п. 5) и **доступ к кассам**.
8. **Начальные остатки касс**: «Кассы» → «Задать начальный остаток». Один раз и только до первой смены и первого документа — используйте суммы из акта инвентаризации на дату начала учёта.

## 5. Пользователи и доступ

1. «Пользователи» → «Создать»: логин (уникален без учёта регистра), ФИО, начальный пароль (10–256 символов, буквы и цифры), роли.
2. Роли: `accountant` — бухгалтер, `cashier` — кассир, `manager` — руководитель (согласует расходы), `auditor` — аудитор (только чтение), `admin` — администратор. Не совмещайте `admin` с финансовыми ролями.
3. «Доступ к кассам» → выдать пользователю кассы. Без доступа пользователь (кроме admin) не видит ни одной кассы; такие пользователи перечислены на панели состояния (W1).
4. Сброс пароля: «Пользователи» → «Сбросить пароль». Все сеансы пользователя отзываются, при входе потребуется смена пароля.
5. Увольнение: снимите флаг «Активен» — доступ прекращается немедленно. Учётные записи не удаляются (они упоминаются в журнале аудита).

Для демонстрации: `node scripts/seed-demo-users.mjs` создаёт по пользователю каждой роли, пароли — в `.runtime/demo-users.json` (не передавать и не коммитить).

## 6. Резервное копирование и восстановление

### 6.1. Плановое копирование

Параметры (переменные окружения контейнера `api`):

| Параметр | Назначение | По умолчанию |
|---|---|---|
| `Backups__IntervalHours` | Интервал плановых копий, ч; `0` — выключено | `0` (**выключено**) |
| `Backups__RetentionDays` | Срок хранения копий, дней | 30 |
| `Backups__EncryptionKey` | Ключ AES-256-GCM | обязателен в production |
| `Backups__Directory` | Каталог копий в контейнере | `/var/lib/faiza/backups` (том `backup-data`) |

В текущем `docker-compose.production.yml` интервал не задан. Добавьте в раздел `environment` сервиса `api` строку `Backups__IntervalHours: 24` (или через `docker-compose.override.yml`) и перезапустите `api`. `[УТОЧНИТЬ У ЗАКАЗЧИКА: требуемая периодичность и срок хранения]`.

### 6.2. Ручная копия и проверки

«Резервные копии» → **«Создать копию»** → **«Проверить»** (контрольная сумма, манифест, расшифровка) → **«Тест восстановления»**. Тест разворачивает копию в одноразовую базу `backup-restore-db`, сверяет остатки касс, суммы задолженностей и платежей, число проведённых документов и внешние ключи с данными на момент копирования, затем очищает базу. Рабочая база не меняется. Подменённая или повреждённая копия отклоняется (422) и фиксируется в журнале аудита.

Рекомендуемый регламент: тест восстановления — не реже раза в месяц и после каждого обновления версии.

### 6.3. Внешнее хранение

Том `backup-data` находится на том же сервере. Регулярно копируйте его содержимое (файлы `cash-*.dump` и манифесты) на внешний носитель или в другое хранилище, например:

```bash
docker run --rm -v faiza-cash_backup-data:/data -v /mnt/offsite:/out alpine sh -c "cp -n /data/* /out/"
```

(имя тома зависит от имени проекта Compose — проверьте `docker volume ls`). Копии зашифрованы, поэтому их можно хранить вне организации; ключ храните отдельно от копий.

Вложения (W1) хранятся в файловом хранилище `api`; включите их каталог в ту же процедуру внешнего копирования (ADR-0008).

### 6.4. Аварийное восстановление рабочей базы

Встроенная функция выполняет только тестовое восстановление. Восстановление рабочей базы — ручная процедура:

1. Остановите `api` и `proxy`: `docker compose -f docker-compose.production.yml stop api proxy`.
2. Выберите последнюю копию, успешно прошедшую тест восстановления.
3. Расшифруйте копию ключом `BACKUPS__ENCRYPTIONKEY`. `[Отдельной утилиты расшифровки в поставке пока нет — предложено агенту backend, см. REPORT-C.md. До её появления расшифровку выполняет разработчик тем же модулем, что используется при тесте восстановления.]`
4. Создайте пустую базу и восстановите дамп под ролью `faiza_migrator`: `pg_restore --no-owner --role=faiza_migrator -d faiza_cash <файл>`.
5. Запустите `provision-runtime` повторно, затем `api` и `proxy`.
6. Проверьте остатки касс по последней кассовой книге и выполните тест восстановления новой копии.

Целевые показатели: RTO ≤ 4 ч, RPO ≤ интервала копирования `[УТОЧНИТЬ У ЗАКАЗЧИКА]`.

## 7. Ротация ключей и паролей

| Секрет | Процедура | Последствия |
|---|---|---|
| `JWT__KEY` | Заменить в `.env`, перезапустить `api` | Ключи доступа (15 мин) становятся недействительными; клиенты автоматически получат новые через refresh-cookie |
| `RUNTIME_DB_PASSWORD` | Заменить в `.env`, `up -d provision-runtime api` (контейнер `provision-runtime` выполняет `ALTER ROLE ... PASSWORD`) | Кратковременная недоступность API |
| `MIGRATION_DB_PASSWORD` | `ALTER ROLE faiza_migrator PASSWORD '...'` в `psql`, затем заменить в `.env` | Нужен при следующем обновлении |
| `BACKUP_RESTORE_DB_PASSWORD` | Заменить в `.env`, пересоздать `backup-restore-db` и `api` | База на `tmpfs`, данных не теряется |
| `BACKUPS__ENCRYPTIONKEY` | Создать новый ключ, сохранить **оба** ключа вне сервера, заменить в `.env`, перезапустить `api`, сразу создать и проверить новую копию | Сервер работает с одним ключом. Копии, сделанные старым ключом, система не проверит и не восстановит (манифест хранит идентификатор ключа); для работы со старой копией временно верните старый ключ |
| Пароль администратора | «Сменить пароль» в профиле | При компрометации — сброс через второго администратора |

Рекомендуемая периодичность — раз в год и немедленно при увольнении лица, имевшего доступ к `.env` `[УТОЧНИТЬ У ЗАКАЗЧИКА]`.

## 8. Обновление версии

1. Создайте копию и выполните тест восстановления.
2. `git pull`, затем `docker compose -f docker-compose.production.yml up --build -d`. Контейнер `migrate` применит новые миграции, `api` запустится только после этого.
3. Проверьте панель состояния (W1): `pendingMigrations = 0`, версия приложения обновлена.

Миграции только добавляются; откат версии с откатом схемы не поддерживается — для отката используйте восстановление из копии (п. 6.4).

## 9. Мониторинг и журналы

- **Панель состояния** (W1, только admin): доступность и версия БД, неприменённые миграции, последняя копия и её проверка, объём вложений и свободное место, активные сеансы, неудачные входы за 24 ч, пользователи без доступа к кассам, версия приложения.
- `GET /health` — проверка доступности для внешнего мониторинга.
- Журналы `api`: `docker compose -f docker-compose.production.yml logs api` (JSON); файлы `.jsonl` в каталоге `Logs__Directory`.
- **Журнал аудита** в интерфейсе: входы, изменения пользователей, доступов, касс, настроек, копий.

Признаки проблем: много неудачных входов (подбор пароля — проверьте IP в журнале), копия старше интервала, свободного места меньше 10 %.

## 10. Безопасность эксплуатации

- Не открывайте порт PostgreSQL наружу — сети `data` и `restore` внутренние.
- Не меняйте права роли `faiza_runtime` на владельца таблиц: это позволило бы отключить триггеры неизменяемости.
- Не запускайте автоматические тесты на рабочей базе: они работают только с базой `*_test` и пересоздают её схему.
- Не передавайте `.env`, `.runtime/*`, файлы `*.dump`.
- Описание API (`/api/openapi/{doc}.json`) доступно только администратору.
