# Сценарий защиты (демонстрация 8–10 минут)

Демонстрация проводится только на синтетических данных (`node scripts/seed-demo.mjs`, `node scripts/seed-demo-users.mjs`). Пароли демо-пользователей — в локальном `.runtime/demo-users.json`; не показывать этот файл на экране.

## Подготовка (до начала, не входит в 10 минут)

1. Запустить систему (Docker Compose или локально), открыть пять вкладок/профилей браузера — по одной на роль, все пользователи уже сменили начальный пароль.
2. В настройках (admin) задан порог согласования, например `10000.00`; загружен логотип.
3. Справочник номиналов заполнен; у сотрудника-контрагента вида «сотрудник» есть выданный аванс со сроком в прошлом (для показателя «просроченные авансы»).
4. Открыта смена в демонстрационной кассе на сегодня.
5. Подготовлен терминал с подключением `psql` к демо-базе (для показа триггера) и сохранённым выводом последнего `node tests/run-all.mjs`.
6. Масштаб браузера 110–125 %, чтобы комиссии было видно.

## Вероятные вопросы комиссии

1. **Почему нельзя просто удалить ошибочный документ?**
   Удаление уничтожает историю и меняет остаток прошлых дат. Исправление — сторно с причиной; оригинал, сторно и правильный документ видны в журнале (ADR-0002).

2. **Что мешает администратору БД изменить проведённую сумму?**
   Триггеры PostgreSQL отклоняют UPDATE/DELETE проведённых документов и аудита. API работает под ролью без прав владельца таблиц, поэтому отключить триггер из приложения нельзя (ADR-0001). Владелец сервера физически может всё — поэтому важны шифрованные внешние копии и регламент доступа.

3. **Как система ведёт себя, если два кассира одновременно тратят последние деньги?**
   Проведение идёт в транзакции Serializable с блокировкой кассы: один расход проходит, второй получает 409. Это проверено тестом с параллельными запросами (ADR-0003).

4. **Почему суммы передаются строкой?**
   Число в JavaScript — `double`, оно не представляет точно 0,1 и теряет точность на больших суммах. Строка + `decimal` на сервере исключают ошибки округления (ADR-0004).

5. **Как обеспечено разделение обязанностей?**
   Администратор не выполняет финансовых операций, автор расхода не может его согласовать, кассир проводит только свои документы. Соответствие матрице прав проверяется автоматическим тестом по всем маршрутам (ADR-0007).

6. **Что будет, если сервер сломается?**
   Плановые резервные копии шифруются AES-256-GCM, проверяются по контрольной сумме и тестово восстанавливаются в отдельную базу со сверкой остатков. Ключ хранится вне сервера. Регламент — в руководстве администратора.

7. **Соответствуют ли печатные формы нормативным требованиям РТ?**
   Формы содержат обязательные реквизиты; точное соответствие утверждённым формам требует сверки с нормативным актом `[УТОЧНИТЬ: акт НБТ/Минфина РТ]` — это отражено в ТЗ как открытый вопрос, а не заявлено без проверки.

8. **Почему собственная разработка, а не готовая программа?**
   Требования к неизменяемости, доступу по кассам, согласованию, авансам и развёртыванию на своём сервере; сравнение аналогов — в главе 1.4.

9. **Как проверяется, что остаток верный?**
   Тест инвариантов сравнивает остаток, рассчитанный прямым SQL, с API остатка, панелью, кассовой книгой, сводкой и CSV — все совпадают до копейки.

10. **Как защищены вложения от вредоносных файлов?**
    Тип определяется по сигнатуре, а не расширению; допускаются только JPEG/PNG/WebP/PDF до 5 МБ; файл отдаётся с запретом определения типа браузером и только после проверки доступа к кассе (ADR-0008).

11. **Как работает пересчёт по купюрам и инвентаризация?**
    Пользователь вводит количество по номиналам из справочника НБТ; сервер точно считает сумму, сравнивает с расчётным остатком и фиксирует разницу в неизменяемом акте.

12. **Как система учитывает несколько валют?**
    Каждая касса работает в одной валюте; переводы между кассами разных валют запрещены. Сводные суммы панели пересчитываются в TJS по курсу на дату, и ответ сообщает, какие курсы использованы.

13. **Какие тесты есть и сколько их?**
    Модульные (правила остатка, смены, деньги, шифрование), тесты клиента, интеграционные на реальном PostgreSQL (безопасность, матрица прав, целостность, отчёты, восстановление), браузерные E2E с проверкой доступности. Числа — по последнему прогону `[вставить]`, см. `docs/TESTING.md`.

14. **Какова производительность?**
    При 20 одновременных пользователях 95-й перцентиль ответа панели — не более 500 мс (автоматический замер). Списки постраничные, справочники кэшируются.

15. **Какова экономическая эффективность?**
    Методика и формулы — глава 4: экономия времени по хронометражу операций до/после, снижение потерь, затраты на разработку и эксплуатацию, срок окупаемости. Числа — по данным заказчика `[УТОЧНИТЬ]`.
